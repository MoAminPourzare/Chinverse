# مسیر یادگیری ChinVerse از پایه تا تغییر مستقل

تاریخ شروع: ۴ اکتبر ۲۰۲۶

هدف: بتوانی ساختار پروژه و مسیر حرکت داده را توضیح بدهی، کدهای فرانت و بک‌اند را بخوانی، دیتابیس را بفهمی، خطاها را پیدا کنی و یک تغییر را از ابتدا تا بررسی نتیجه انجام بدهی.

این برنامه بر اساس بررسی اولیهٔ فایل‌های پروژه نوشته شده است. وضعیت اجرای زندهٔ سرویس‌ها در این جلسه بررسی نشده است. با ادامهٔ توسعه، برنامه و دفتر پیشرفت نیز به‌روز می‌شوند. شمارهٔ این فازهای آموزشی مستقل از شمارهٔ فازهای انتشار در اسناد قبلی پروژه است.

## روش هر جلسه

۱. مفهوم موردنیاز بخش بعدی پروژه و پیش‌نیازهای آن را مشخص می‌کنیم.
۲. ابتدا یک آموزش مستقل و مفصل، بدون فرض آشنایی با چین‌ورس، ارائه می‌دهیم: مسئله، مفهوم، زبان/فناوری مربوط، شیوهٔ استفاده و دلیل آن.
۳. از مثال‌های ساختگی کوچک شروع می‌کنیم و به مثال کامل قابل اجرا می‌رسیم؛ ورودی، مراحل اجرا، خروجی، حالت ناموفق و اشتباه‌های رایج را توضیح می‌دهیم.
۴. تمرین‌های مرتبط همراه پاسخ و توضیح ارائه می‌شوند؛ ادامهٔ گفتگو به آزمون اجباری وابسته نیست.
۵. پس از خواندن این بخش آموزشی و پاسخ به سؤال‌ها، به فایل‌های چین‌ورس برمی‌گردیم و کاربرد همان مفاهیم را در کد واقعی دنبال می‌کنیم.
۶. در پروژه، نقش هر فایل و ارتباطش با فایل‌های دیگر را بررسی می‌کنیم و اثر کد را در خروجی می‌بینیم.
۷. این چرخهٔ «آموزش مستقل → کاربرد در چین‌ورس» برای موضوع بعدی تکرار می‌شود.
۸. نقطهٔ مطالعه، ابهام‌ها و شاهد تمرین را در دفتر پیشرفت ثبت می‌کنیم؛ صرف ارائهٔ مطلب را تسلط ثبت نمی‌کنیم.

هر اصطلاح تازه هنگام اولین استفاده توضیح داده می‌شود. اگر در یک فایل مفهوم پیشرفته‌ای باشد، ابتدا نقش آن را می‌فهمیم و بررسی عمیق را به جلسهٔ دارای پیش‌نیاز مناسب ارجاع می‌دهیم. یک فایل طولانی می‌تواند چند جلسه داشته باشد.

معیار پیشرفت، توانایی توضیح و انجام تمرین است؛ سرعت تمام‌کردن فایل‌ها معیار نیست.

ترجیح یادگیرنده، به‌روزشده در ۱۱ اکتبر ۲۰۲۶: او توضیح قبلی را فقط تا شروع بحث `use client` خوانده و بخش پس از آن خوانده نشده است. آموزش مستقیم از روی پروژه هنوز برای او دشوار است. در ابتدای هر بخش، آموزش مستقل، حرفه‌ای، مفصل و خودبسنده با مثال غیرپروژه‌ای لازم است؛ سپس کاربرد آن در چین‌ورس بررسی می‌شود. طول زیاد آموزش ایرادی ندارد؛ دامنهٔ هر درس باید منسجم و پیش‌نیازها روشن باشند. اصطلاح‌ها و پیش‌نیازها را از روی نامشان معلوم فرض نکن. مثال آموزشی را از کد واقعی و دادهٔ فرضی را از دادهٔ واقعی متمایز کن. موضوع‌های آشنا یا توضیح‌های بلند را فقط وقتی خود یادگیرنده درخواست کرد کوتاه کن. تا اعلام آمادگی برای کاربرد، از درس مستقل به ادامهٔ کد پروژه نپر.

در آغاز آموزش، یادگیرنده خواست پاسخ تمرین نیز توسط مدرس توضیح داده شود. مثال‌ها و پاسخ‌ها را ارائه می‌کنیم و برای ادامه منتظر آزمون یا پاسخ اجباری نمی‌مانیم؛ یادگیرنده هرجا لازم بداند سؤال می‌پرسد.

تنظیم سطح در ۱۷ اکتبر ۲۰۲۶: کاربر دانشجوی کامپیوتر است و با چند زبان کار کرده؛ توضیح دوبارهٔ متغیر، شرط، حلقه و اصول عمومی تابع لازم نیست مگر خودش درخواست کند. تمرکز روی ویژگی‌ها و الگوهای خاص JavaScript/TypeScript، React و Next.js باشد. آموزش مستقل همچنان مفصل و همراه چرایی و مثال است؛ پس از کامل‌شدن یک واحد مشخص، همان مفاهیم در کد فعلی چین‌ورس آموزش داده شوند. پایان یک واحد را از پایان کل آموزش زبان/فریم‌ورک متمایز کن.

## نقشهٔ اولیهٔ پروژه

| بخش | فناوری‌های مشاهده‌شده | فایل‌های مرجع |
| --- | --- | --- |
| رابط کاربری و مسیرهای وب | Next.js، React، TypeScript، Tailwind CSS | `frontend/package.json`، `frontend/src/app`، `frontend/src/components` |
| ارسال درخواست و واسطهٔ سرور Next.js | Axios، Route Handler | `frontend/src/lib/api.ts`، `frontend/src/app/api/backend/[...path]/route.ts` |
| برنامهٔ بک‌اند | Python، FastAPI، Uvicorn، Pydantic | `backend/pyproject.toml`، `backend/app/main.py`، `backend/app/api`، `backend/app/schemas` |
| دسترسی به داده و تغییر ساختار آن | PostgreSQL، SQLAlchemy، asyncpg، Alembic | `backend/app/db/session.py`، `backend/app/models`، `backend/alembic` |
| تست و بررسی کد | Vitest، Testing Library، Playwright، pytest، ESLint، Ruff | تنظیمات تست، `frontend/e2e`، `backend/tests`، `scripts/check.ps1` |
| استقرار مستندشدهٔ آزمایشی | GitHub Actions، Vercel، Hugging Face Spaces، Neon | `README.md`، `.github/workflows`، اسناد استقرار در `docs` |

مسیر معمول درخواست HTTP از کد مرورگر:

```text
صفحه یا کامپوننت React در مرورگر
  → تابع سرویس در frontend/src/services یا کد فراخوانندهٔ API
  → Axios در frontend/src/lib/api.ts
  → مسیر /api/backend/... در سرور Next.js
  → مسیر متناظر /api/v1/... در FastAPI
  → اعتبارسنجی و منطق برنامه
  → SQLAlchemy و اتصال دیتابیس
  → PostgreSQL
  → پاسخ و به‌روزرسانی صفحه
```

این نقشه برای درخواست‌های معمول مرورگر است. ساخت اولیهٔ صفحه روی سرور، WebSocket چت و دریافت رسانه را جداگانه بررسی می‌کنیم. Next.js نیز کد سمت سرور دارد؛ نام پوشهٔ `frontend` به معنی اجراشدن تمام محتویات آن در مرورگر نیست.

۷. فعالیت روزانه، تنظیمات و قابلیت‌های معرفی دوستان، امتیاز و اشتراک بر اساس وضعیت واقعی کد.

خروجی: بتوانی بفهمی برنامهٔ آنلاین روی کدام سرویس اجرا می‌شود، داده و فایل‌هایش کجا هستند و خطای انتشار را از کجا پیگیری کنی.

- ۹.۳: یک تغییر ظاهری مستقل و بررسی نتیجه.
- ۹.۴: یک تغییر رفتاری با API و تست مرتبط.
- ۹.۵: یک قابلیت کوچک شامل تغییر model، migration، API و رابط کاربری در محیط آموزشی.
- ۹.۶: مرور فایل‌های باقی‌مانده و توضیح طرح تغییر قبل از اجرا.

عیب‌یابی و تست از جلسه‌های اول معرفی می‌شوند؛ این فاز محل جمع‌بندی عملی آن‌هاست.

خروجی: بتوانی برای یک نیاز جدید، فایل‌های لازم را پیدا کنی، تغییر را انجام بدهی، نتیجه را بررسی کنی و دلیل تصمیم‌هایت را توضیح بدهی.

## پوشش فایل‌ها و فناوری‌ها

برای جلوگیری از جاافتادن بخش‌ها، هنگام ورود به هر پوشه فهرست فایل‌های آن را ثبت و برای هر فایل وضعیت تعیین می‌کنیم: «معرفی‌شده»، «بررسی‌شده»، «تمرین‌شده» یا «نیازمند بازگشت».

- سورس فرانت و بک‌اند، تست‌ها، migrationها، اسکریپت‌ها و تنظیمات پروژه با توجه به نقششان بررسی می‌شوند.
- برای CSV، JSON، زیرنویس و رسانه‌ها، ساختار، منبع و مسیر ورود و استفاده در برنامه را می‌فهمیم.
- برای عکس، آیکون، فونت و فایل‌های طراحی، مسیر استفاده و شیوهٔ جایگزینی را بررسی می‌کنیم.
- برای `node_modules`، محیط مجازی، cacheها، خروجی build، `.pyc`، lockfileها و گزارش‌ها، توضیح می‌دهیم چه چیزی آن‌ها را می‌سازد، چه مسئولیتی دارند و چگونه مدیریت می‌شوند. تمرکز خواندن خط‌به‌خط روی کد و تنظیمات متعلق به پروژه است؛ فایل‌های تولیدشده و کتابخانه‌ها در حد نیاز به اجرا و عیب‌یابی بررسی می‌شوند.
- مقادیر محرمانهٔ `.env` وارد متن آموزشی نمی‌شوند؛ مفهوم تنظیمات را با `.env.example` و نمونهٔ غیرمحرمانه یاد می‌گیریم.

برای هر فناوری این پرسش‌ها را جواب می‌دهیم: چیست؟ کدام مسئله را حل می‌کند؟ اینجا چگونه استفاده شده؟ مزیت و محدودیتش چیست؟ جایگزین آن چه اثری بر این پروژه دارد؟

اگر دلیل تاریخی انتخاب یک فناوری در اسناد ثبت نشده باشد، کاربرد قابل مشاهده و دلیل فنی مناسب‌بودن آن را توضیح می‌دهیم و آن را به‌عنوان تصمیم اولیهٔ قطعی معرفی نمی‌کنیم.
